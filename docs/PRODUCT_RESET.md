# Concert Passport 产品重置

**状态：** 产品骨架评审稿
**日期：** 2026-08-23
**原则：** 先确定用户为什么来、完成什么、为什么回来，再讨论视觉风格。

## 1. 上一版为什么失败

上一版 Concept Lab 停止使用。失败不是某个颜色或版式的问题，而是方法有误。

1. 把“情绪价值”写成了界面台词，例如“等待也值得被记住”“旅程正在长大”。产品替用户表达感受，显得刻意。
2. 用三个命名概念证明设计方向，页面首先在展示设计手法，而不是帮助用户完成任务。
3. 加入准备度、同行分工、路线章节等当前产品没有的数据与行为，原型无法代表真实产品。
4. 默认用户已经保存一场演出，忽略了第一次进入、没有公布场次、正在比较城市等更常见状态。
5. 把艺人图片当成情绪，把票夹、印章、日记当成定位。真实情绪应该来自“我关注的人、我想去的场、我去过的记录”。
6. 文案解释太多，行动太少；平台不断描述自己，却没有清楚回答“现在有什么与我有关”。

## 2. 真实产品能力

以下以当前代码和生产数据为准。

### 已经可用

- 按艺人、地区、日期搜索亚太 K-pop 演出。
- 从多个来源合并演出，识别重复记录。
- 展示日期、城市、场馆、官方活动或售票页面。
- 关注“艺人 + 地区”。
- 把演出保存到当前匿名会话或账号。
- 查看已保存的未来演出。
- 手动添加去过的演出，查看场次、艺人、城市和距离统计。
- 注册、登录以及匿名数据迁移。

### 后端已有基础、前台没有形成体验

- 演出版本与变更记录。
- 官方链接核验时间与来源证据。
- 定时刷新已关注的艺人和地区。

### 目前并不存在

- 可浏览的艺人详情页。
- 与用户关注/保存相关的更新流。
- 实际通知投递与通知设置。
- 购票生命周期任务、提醒和完成状态。
- 同行分工、酒店、交通、预算或路线规划。
- 已保存演出一键转为 Passport 记录。
- 编辑、删除、取消保存和关注管理。

产品页面必须区分“已经可靠工作”“需要补齐”“长期设想”，不能把路线图当成当前能力。

## 3. 当前可成立的定位

现阶段最诚实、也最有机会形成闭环的定位是：

> 帮助亚太 K-pop 粉丝关注想看的艺人，找到可信的场次和官方页面，把想去与去过的演出留在同一个地方。

这句话包含三个连续动作：

```text
关注谁 → 找到并保存一场 → 看完后进入 Passport
```

“不遗漏关键票务变化”是下一层价值，但在更新流和通知交付真正建立以前，不能作为已经实现的承诺。

## 4. 用户问题，不是用户画像

年龄、性别和审美不是首页信息架构。更稳定的是用户当下的问题。

| 用户状态 | 她真正的问题 | 页面应该回答什么 |
|---|---|---|
| 第一次进入 | 这里有没有我想看的艺人？ | 先关注谁；覆盖哪些地区 |
| 已关注、无场次 | 有消息时我能看到吗？ | 正在关注什么、最近检查时间、官方覆盖范围 |
| 同一巡演有多城 | 哪一场适合我？ | 日期、城市、场馆、售票状态、官方来源 |
| 决定想去 | 以后从哪里回来查看？ | 保存成功、与这场有关的最新状态 |
| 官方页面变化 | 这条更新与我有什么关系？ | 什么变了、什么时候变、去哪里确认 |
| 演出结束 | 我想把它留下来 | 去过/没去；自动带入已知信息 |
| 回看 Passport | 我看过什么？ | 艺人、城市、时间顺序和真实记录 |

用户讨论中反复出现的不是“缺少漂亮的演唱会 App”，而是更朴素的问题：不知道预售已经开始、不清楚该关注哪些官方渠道、跨国票务规则不同、保存和提醒不可信、历史记录重复或丢失。

## 5. 核心闭环

### 5.1 第一次使用

首页不展示一个随机的亚洲演出作为主角。

1. 搜索艺人。
2. 选择愿意关注的地区；默认可以是全部亚太。
3. 关注艺人。
4. 进入艺人页查看已公布场次。

如果用户暂时不想设置，可以继续浏览近期演出，但浏览不是首页的唯一入口。

### 5.2 艺人页

这是当前信息架构最大的缺口。

艺人页只负责：

- 是否已关注以及关注地区；
- 已公布的未来场次；
- 按日期排列的城市；
- 每一场的官方页面状态；
- 没有场次时的明确空状态；
- 用户去过该艺人的历史次数。

它不需要粉丝社区、艺人资讯、音乐播放或模拟亲密关系。

### 5.3 演出详情

按决策顺序展示：

1. 艺人、巡演、城市、日期、场馆。
2. 当前官方状态：已公布 / 官方页面已发布 / 官方售票页已发布。
3. 一个主动作：`标记为想去` 或 `查看已保存内容`。
4. 官方页面；清楚显示目标网站和核验时间。
5. 信息来源和更新时间。
6. 同一巡演的其他城市。

地图和大幅艺人图片都不是必要信息，可以在不影响上述顺序时出现。

### 5.4 回访首页

首页不是推荐流，而是个人状态页。

优先级：

1. 与我有关的变化；
2. 最近一场想去的演出；
3. 关注艺人的新场次；
4. 没有个人内容时，才展示区域近期演出。

“与我有关的变化”必须是事实：新场次、日期变化、场馆变化、官方页面发布、售票页面发布或取消。没有变化时不制造内容。

### 5.5 演出结束

已保存演出结束后出现一个明确问题：`你去过这场吗？`

- `去过`：使用已有艺人、场次、日期、场馆、城市创建 Passport 记录；用户只补充可选内容。
- `没去`：从未来计划移出，不创建 Passport 记录。
- `稍后回答`：保留在待确认区，不反复催促。

这一步把实用价值和情绪价值真正连接起来，不需要额外写一段抒情文案。

## 6. 信息架构

### 主导航

| 建议名称 | 页面职责 | 替代当前 |
|---|---|---|
| 首页 | 个人更新、最近想去、关注艺人的新场次 | 今日 |
| 找演出 | 搜艺人、看艺人页、按地区/日期浏览 | 地图 / Atlas |
| 想去 | 已保存的未来演出和结束后的待确认 | 计划 |
| Passport | 真实去过的演出 | Passport |

地图是“找演出”的一种查看方式，不应成为用户必须理解的产品栏目。信息源目录进入演出详情和设置，不占主导航。

### 必须新增的页面/视图

- 艺人页 `/artists/[artistId]`
- 个人更新区
- 关注管理
- 已保存演出的结束确认
- Passport 记录详情及编辑

## 7. 内容原则

### 只写用户需要知道的事实

不写：`你的旅程，正在慢慢长大。`
改为：`已保存 2 场演出。`

不写：`离见到 LeeHi 还有 5 天。`
改为：`LeeHi · 布里斯班｜8 月 28 日 19:00`
倒数可以是辅助信息：`5 天后`。

不写：`今天只做一件事。`
改为：`官方售票页已发布。`

不写：`让每一次奔赴都被珍藏。`
改为：`记录去过的演出。`

### 使用稳定、自然的用户词汇

- `关注`，而不是“进入雷达”。
- `想去`，而不是“创建行程”。
- `去过`，而不是“验证出席”。
- `找演出`，而不是“探索 Atlas”。
- `官方页面`，并显示网站名称。
- `场馆当地时间`，仅在跨时区时补充用户本地时间。

### 不替用户表达感情

界面可以承载用户自己的艺人、日期、照片和记录；平台不替她定义“相遇、奔赴、心动、陪伴”或与艺人的关系。

## 8. 功能优先级

### P0：让现有闭环成立

1. 艺人页。
2. 首页个人状态与更新。
3. 关注管理。
4. 取消保存。
5. 已保存演出转 Passport。
6. Passport 编辑/删除与重复检测。

### P1：兑现票务保护

1. 演出变更可见性。
2. 官方链接发布提醒。
3. 通知偏好和交付状态。
4. 关键票务阶段的数据模型与运营能力。

### 以后再决定

- 同行协作。
- 旅行预订和路线。
- 照片、setlist 和分享卡。
- 公开社区与社交关系。

## 9. 评审标准

下一版先用无视觉装饰的线框稿回答：

1. 新用户是否能在 30 秒内关注一位艺人？
2. 用户能否看懂为什么这一场出现在这里？
3. 用户能否区分“官方活动页”和“官方售票页”？
4. 保存一场以后，是否知道以后在哪里找到它？
5. 回访首页是否只出现与用户相关的内容？
6. 演出结束后是否能用一次确认进入 Passport？

上述问题没有通过前，不进入新的视觉风格探索。
