# 发布与维护流程

仓库当前 package version 为 `0.1.0`，处于 early access。历史文档中的 v27–v32 是交付批次标记，不是已经创建的 SemVer GitHub Releases。尚未发布的仓库改动记入 [Unreleased](../CHANGELOG.md#unreleased)，真正发布时才填写 tag 和日期。

## 形成可 review 的候选

1. 检查 `git status`，识别本次改动与已有未提交工作；不要把别人的工作一并提交。
2. 在合成数据或数据库副本上运行 `npm run check`；影响原生/生命周期时运行 Swift 核心测试，UI 检查桌面与小屏。
3. schema 变化验证迁移、用户数据指纹与旧应用读取候选新库的边界；上线数据库保持服务端来源。
4. 文档、环境模板、第三方素材说明与 CHANGELOG 与实现一致。区分真实验收、历史快照和计划。
5. 检查未跟踪素材已纳入候选；检查当前文件及 Git 历史中的凭证、备份和个人信息。`.gitignore` 不会清理已经进入历史的内容。

## 代码发布

维护者确认版本和发布范围后，再同步根目录/Web package version 与锁文件，在 CHANGELOG 记录日期、行为变化、迁移与验证边界。提交聚焦改动，等待远端 CI 通过，然后创建对应 tag / Release。不存在“创建 tag 自动部署”的当前工作流。

初次公开前的 About、Topics、社交预览、文案与许可检查见[展示资料](SHOWCASE.md)。仓库可见性变化属于独立发布决定；公开前尤其检查历史、第三方媒体和隐私记录。

## 应用部署

按[部署与恢复](../deploy/README.md)准备一致性备份、候选镜像与回滚路径。先在数据库副本上验证，再切换应用与 worker；检查 `/api/health`、关键页面、用户数据与采集状态。应用健康与目录新鲜度分开验收。

应用回滚优先使用旧镜像并保留新增用户写入。恢复数据库属于灾难恢复，需要先停写、保留故障文件并核对备份之后的写入，不能覆盖线上库“解决”迁移问题。

## 持续维护

- Dependabot 按配置提出 npm 与 GitHub Actions 更新，维护者 review；不会自动合并或强制升级 major。
- 在依赖更新、来源结构变化、字段冲突或用户反馈出现时补充对应验证；不为了展示重复跑无关全量检查。
- 安全问题按 [SECURITY](../SECURITY.md)处理；社区争议按[行为准则](../CODE_OF_CONDUCT.md)处理。
- 发布说明明确新增能力、已知限制与部署要求，让 Watch → Releases 的读者得到有意义的更新。
