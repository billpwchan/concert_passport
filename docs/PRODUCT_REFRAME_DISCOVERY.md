# Concert Passport 产品重构探索

**状态：** 本地讨论稿，不代表已确定方向
**日期：** 2026-08-23
**范围：** Web 产品关系、首页信息架构、视觉语言与情绪体验

## 1. 先说结论

现有产品并不缺少完成度。它已经具备清晰的数据边界、官方来源、跨城市发现、计划、Passport 和记忆闭环，也有成熟的响应式实现。真正的问题是：

> 现在的首页首先告诉用户“亚洲接下来有什么演出”，而年轻粉丝真正想先确认的是“我喜欢的人下一场在哪里、我离见到 TA 还有多久、我和朋友准备到哪一步、这段经历最后会留下什么”。

这是产品主语的问题，不只是视觉风格的问题。

现有体验的主语是“平台拥有的演出数据库”；重构后的主语应该是“用户正在经历的追星旅程”。官方数据与严谨能力不需要减少，而应退到体验的骨架里。

## 2. 项目现状判断

### 已经成立的资产

- 演出、艺术家、城市、票务来源和用户计划已经是可工作的真实对象。
- `Today → Atlas → Plans → Passport` 的生命周期逻辑是对的。
- 官方来源、时间区、卖家边界和隐私规则构成了长期信任资产。
- 现有深色大图方向具有很高的视觉完成度，能承载真实艺人和巡演素材。
- Web 已具备英语、简体中文、繁体中文以及桌面/移动响应式能力。

### 当前体验的错位

1. **首页像媒体首页，不像我的首页。** 未登录用户首先看到一个亚洲演出封面；已登录状态仍缺少强烈的“这是我的旅程”感。
2. **数据库语言压过了粉丝语言。** `Upcoming across Asia`、来源、城市和状态都准确，却很少表达期待、投入、同行和纪念。
3. **严谨被视觉化成了商务。** 全大写、窄字距、黑底、硬边、目录式导航与来源标签叠加后，像高端票务 B2B 或音乐行业刊物。
4. **年轻化目前主要依赖艺人图片。** 一旦没有图片，界面就会迅速回到冷静工具；产品自身缺少有记忆点的情绪组件。
5. **计划与回忆仍像两个栏目。** 理论上同一事件会从计划进入 Passport，但界面还没有让用户在准备阶段预感到“这一页以后会成为我的回忆”。
6. **桌面完成度高于手机亲密感。** 手机首屏视觉冲击强，但主要是观看海报；用户的计划状态、朋友、准备度和私人叙事没有进入首屏。

## 3. 用户不是一个年龄标签

“30 岁以下、女性居多”只能作为招募与传播假设，不能直接变成粉色、贴纸或可爱字体。更有用的是把核心用户理解为几种会切换的心理状态：

| 心理状态 | 用户脑中的问题 | 产品应该给出的感受 |
|---|---|---|
| 刚看到消息 | 真的有这场吗？我来得及吗？ | 被接住、可信、不慌 |
| 准备抢票 | 我还差什么？谁负责？ | 有同伴、有把握、清楚 |
| 等待见面 | 还有多久？这段等待值得吗？ | 期待正在累积 |
| 出发途中 | 我们真的要去见 TA 了 | 仪式感、共同经历 |
| 散场以后 | 这一晚不要消失 | 被珍藏、可以回看 |
| 下一次巡演 | 我已经走过多远？ | 连续性、身份与成长 |

因此，情绪价值不是“更兴奋的 UI”，而是把五种价值同时做出来：

1. **期待感：** 倒数的是一次将要发生的相遇，而不是一个数据库日期。
2. **投入感：** 每一步准备都成为旅程的一部分，而不是待办清单的消耗。
3. **陪伴感：** 平台像票务群里最靠谱的朋友，不模拟艺人私聊，也不制造虚假亲密。
4. **归属感：** 同行朋友、城市、应援与共同经历可以被看见，但不靠公开粉圈竞争。
5. **纪念感：** 计划中的事件从第一天就在生长为 Passport 记录。

## 4. 研究如何影响设计

- 2024 年针对 K-pop 演唱会参与者的视觉民族志把核心体验概括为自我扩展、归属、满足、集体身份和共同情绪。这说明“去现场”本身是一段身份变化，而不是一次票务交易。[研究摘要](https://www.sciencedirect.com/org/science/article/abs/pii/S275266662400007X)
- 2025 年关于 K-pop 周边与身份的研究将小卡、灯棒等物件描述为忠诚、参与、仪式与社区连接的载体。产品可以借鉴“可珍藏物件”的交互逻辑，但不能照搬随机稀缺和消费压力。[Harmonia 研究](https://journal.unnes.ac.id/journals/harmonia/article/view/24450)
- 2024 年关于 “K-pop girlies” 与小卡收藏的质性研究把收藏放在女性生活经验、人际沟通和社区建构中，而不是简单归因于可爱审美。[论文记录](https://ir.ua.edu/items/26518783-4386-4ff9-b646-49396c545543)
- Weverse 在 2025 年把艺人日程、提醒、书签、通知与社区放在同一艺人语境下；用户不是先进入一个全球日历，而是先进入“我的艺人”。[Calendar 更新](https://weverse.io/notice/27504)、[后续分享与通知更新](https://weverse.io/notice/29130)
- Polarsteps 把计划、同行、照片、路线、统计、回顾和实体旅行书连接成同一段旅程，证明“过程自动长成回忆”比独立纪念模块更自然。[App Store](https://apps.apple.com/us/app/polarsteps-travel-tracker/id947925763)
- Concert Archives 的价值集中在日记、照片、同行、回看和周年提醒，说明过去的演出必须能主动回到今天，而不只是静态档案。[App Store](https://apps.apple.com/in/app/concert-archives/id1531993239)

这些证据不等于用户验证。正式选定方向前，仍需用 8–12 位目标用户完成概念访谈和可用性测试，尤其覆盖高中生、大学生、刚工作的跨城粉丝与至少两种地区票务习惯。

## 5. 三个产品方向

这三者不是可切换主题，而是不同的首页主语与交互结构。

### A. 心动倒数 / Companion Home

**产品关系：** 一个懂票务又懂期待的陪伴者。
**首页主语：** 我离下一次现场还有多久。
**核心组件：** 情绪化倒数、今天只做一件事、旅程生长条、同行朋友、记忆预告。

适合：建立最广泛的年轻用户第一印象；能在不牺牲可信度的情况下显著降低商务感。

风险：文案稍过就会落入虚假亲密；必须描述用户自己的感受，不能替艺人说话。

### B. 应援工具包 / Fan Kit

**产品关系：** 追星小队的共享作战包。
**首页主语：** 这场我们准备到哪一步。
**核心组件：** 可拿起的票夹对象、准备度、任务卡、角色分工、时间窗、可验证链接。

适合：把最有差异化的票务生命周期做得年轻、好用、可传播；移动端转化会比较强。

风险：容易变成游戏化待办。禁止连续签到、稀有度、排行榜、亏损恐惧和强制分享。

### C. 巡演日记 / Journey Diary

**产品关系：** 一本自动记录追星人生的旅行日记。
**首页主语：** 这一场在我的人生里走到哪一章。
**核心组件：** 路线章节、同伴、准备片段、当天记录、散场后的照片/文字/统计回流。

适合：形成最强的长期品牌、Passport 与付费实体产品潜力。

风险：演出前的紧急操作不能被叙事遮住；抢票窗口必须自动切换到更直接的操作模式。

## 6. 当前推荐

首轮建议以 **A 为主骨架、吸收 B 的任务对象和 C 的旅程连续性**。

原因不是 A 最“好看”，而是它能先解决最大的关系错位：让用户感觉首页属于自己。B 更适合成为 Plans 与票日模式的深层语言，C 更适合成为 Journey 与 Passport 的长期品牌语言。

建议的信息架构：

```text
首页：心动倒数 + 今天只做一件事 + 我的艺人近况
  ↓
Journey：应援工具包 + 生命周期 + 同行责任
  ↓
Passport：巡演日记 + 路线 + 照片 + 周年回看
```

## 7. 不应该做的“年轻化”

- 不把女性用户简化为粉色、糖果色、圆角和贴纸。
- 不用艺人第一人称、模拟私信、暧昧通知制造虚假亲密。
- 不用盲盒稀有度、签到、排行榜和消费战绩制造身份压力。
- 不把所有信息做成卡片；对象感要服务于票、旅程、照片和纪念品的真实含义。
- 不降低来源、时区、资格和官方链接的可见性。
- 不让视觉依赖未经许可的艺人图片或粉丝上传素材。
- 不在未验证用户需求前重构整个数据层或现网部署。

## 8. 下一轮验证问题

1. 首屏看到“离见到 TA 还有 X 天”时，用户觉得被理解，还是觉得太做作？
2. 用户更想在首页看艺人动态、自己的下一场，还是全区域新演出？三者的优先级如何因阶段变化？
3. “准备度”是否能降低焦虑，还是会制造新的负担？
4. 高中生能否一眼理解票务阶段、来源可信度和当地时间？
5. 同行朋友应该在什么阶段出现，默认暴露多少信息？
6. 散场后，照片、文字、路线、数据和 setlist 哪一项最能触发主动记录？
7. 哪些界面表达被用户认为“像粉丝做的”，哪些反而显得品牌在模仿粉圈？

## 9. 近期实施边界

- 保留现有 API、数据库、来源管线与生产部署架构。
- 先在独立 Concept Lab 中验证首页关系与组件，不接真实写操作。
- 方向确认后再抽取新 token 和组件，逐页迁移 Today、Plans、Journey、Passport。
- Atlas 的信息密度可以保留较强工具性，但入口和结果应回到“我的艺人/我的旅行”。
- 所有生产变化在本地完成测试与构建后，以本项目独立容器替换；不修改 JChart、Flightlog 或共享网络。
